## Is Force Graph / Knowledge Graph Actually Useful?

| Use case | Force graph helps? |

| "What are the major themes?" | Yes — clusters reveal communities |
| "Find a specific node" | No — search is faster |

For your DB specifically: the value is showing *which AI projects share organizations/categories* without anyone having to query it. The visual pattern IS the insight.

## How Cosmograph Creates Clusters

Same physics as your vis-network, but the **visual result looks better** because of how they tune and render it:

1. **Gravity toward cluster centroid** (not just global center) — once a community starts forming, a weak inward pull keeps it cohesive without collapsing it
2. **Strong inter-node repulsion** — pushes unconnected groups apart so white space forms between clusters
3. **Long springs** — connected nodes stay far enough apart that you can see the edges, not just a blob
4. **GPU rendering** — 60fps at 78k nodes means you can watch it settle in real time, which is itself informative

This is basically identical to your current barnesHut setup — the physics principle is the same.

## What Cosmograph Has That Your Explorer Doesn't (Visually)

| Feature | Cosmograph | Your explorer |
|---|---|---|
| **Node glow / bloom effect** | Yes (WebGL post-processing) | No |
| **Edge color = source node color** | Yes, with opacity falloff | Flat gray |
| **Dark background** | Yes — makes colors pop | Light/mixed |
| **Node size encodes degree** | Yes by default | Fixed size |
| **Timeline scrubber** | Yes (linked histogram) | No |
| **Lasso select** | Yes | Partial |
| **Cluster label overlays** | Yes (computed, float above) | No |
| **GPU rendering** | Yes (WebGL) | No (DOM/SVG via vis-network) |
| **Density-based opacity** | Dense areas fade edges, sparse pop | All edges same weight |

The single biggest visual difference: **edge opacity proportional to node degree**. Dense hubs have faint edges (otherwise it's a hairball); peripheral nodes have bold edges. This is what makes the "galaxy" look instead of a mudball.

## How Obsidian Local Graph Works

You open a note → right-click → "Open local graph." The graph shows:
- **Depth 1**: only notes directly linked to/from this note
- **Depth 2**: those notes' neighbors too
- **Slider**: you drag it from 1 to 4 hops — the graph expands outward in real time
- **Toggles**: show/hide incoming links, outgoing links, "neighbor links" (edges between non-focal nodes)

The cognitive model is **ego-network exploration** — you're always centered on one node and exploring outward. This is very different from the global view. For your DB, an equivalent would be: click a project → graph collapses to show only that project's org, categories, and their other projects.

---

## How Sigma.js Demos Handle Sizing and Clusters

The [Sigma.js demo](https://www.sigmajs.org/demo) uses **Graphology** under the hood:
1. **Community detection**: runs Louvain algorithm on load → assigns each node a `community` integer
2. **Node color**: mapped from community ID → each cluster gets a distinct hue
3. **Node size**: mapped from degree (edge count) → hubs are visually large, leaves are tiny dots
4. **Layout**: ForceAtlas2 run offline, positions baked into the data file — so the graph loads pre-settled into clusters, no physics needed at runtime
5. **Interaction**: hover a node → all non-neighbor edges fade to ~5% opacity (neighbor highlighting)

The degree-based sizing + community coloring combo is what makes it immediately readable — you can see hierarchy (big hub vs. small leaf) AND grouping (same color = same cluster) at a glance.

---

**Bottom line for your project**: the two highest-ROI improvements based on all of this would be (1) size nodes by their edge count and (2) fade edge opacity for high-degree nodes. Those alone would make it look dramatically more like Cosmograph/Sigma without changing the physics at all.

## Litmaps chronological layout — implementation spec

**1. Axes & node positioning**
- **X axis = publication date** (older left, newer right). Default mode is **"Compact"** (papers evenly spaced by date; a citing paper is placed left of the paper it cites). Other X options: **Title Similarity** (SPECTER embeddings + UMAP), **Publication Date** (true linear chronological).
- **Y axis** defaults to **"Compact"** — a custom optimizer with three goals: (a) spread nodes vertically to avoid label collisions, (b) keep a paper's y stable across maps, (c) minimize total citation-line length. Other Y options: **Citations**, **Citations (Log)** (highest at top), **Title Similarity**. Additional sortable axes exposed in the editor: **Cite Count, Ref Count, Publication Date, Momentum** (citations adjusted for recency), **Map Connectivity** (citations within this map).
- Net effect: impactful recent papers land **top-right**.

**2. Node styling**
- Nodes are **dots** ("Dots represent articles"). **Size = log(citation count)**, or constant size (toggle).
- **Color**: user-assignable "Halo color" / icon per article, and color-coded by sub-topic/tag; overlaying two maps shows shared papers in mixed colors (e.g., red+orange).
- **Labels — 6 modes**: Keyword, Author Year, Author Year (All), Title, Compact, Off. Collision rule: **when two labels overlap, only the higher-cited paper's label renders** (except "Author Year (All)").

**3. Edges/citations**
- Lines = citation relationships, toggleable on/off. Direction encoded **positionally** (cited paper sits left of citer) rather than by arrowheads. Public docs don't confirm curved vs. straight; observed renders are thin, subtle lines — the Compact algorithm explicitly **minimizes total line length**, so edges are short connectors, not a dense hairball.

**4. Density/overlap handling**
- Compact Y is the key trick: instead of stacking every same-year paper in one vertical line, it perturbs y-values to **prevent label overlap** while keeping connected papers close. This is what avoids the "everything piled on one date column" problem of a strict timeline.

**5. Seed map / pivot interaction**
- Start from one or more **seed papers**; Litmaps auto-pulls cited + citing works. Expand iteratively via **"More like this" / "Add to Litmap"**, which adds nodes and re-runs discovery (forward/backward citation chaining). **Monitor** sends email alerts when new connected papers appear. New papers slot into the timeline by their own publication date, so the map grows rightward over time.

**Comparison (what's distinctive):**
- **Connected Papers**: *similarity* force-directed graph (not citations). Similar papers cluster spatially; node size = citations, **color shade = publication year**. No time axis — time is a color gradient.
- **ResearchRabbit (Timeline view)**: also X = year, Y = citation count. Nodes **green = in your collection, blue = not**, **darker blue = more recent**. Simpler than Litmaps (no Compact optimizer, no semantic-similarity axis).
- **Litmaps signature look**: a left-to-right time flow with a *non-strict* vertical spread (Compact), log-sized citation dots, sparse short citation lines, top-right = recent+impactful, and per-paper halo colors/labels. That gentle vertical jitter + minimized edge length is what reads as "Litmaps" rather than a generic force layout or a rigid scatter.

# How the best embedding explorers make maps look good

## 1. Making the scatter look like a clean "map"

- **Alpha for density, not just points.** The single biggest lever is per-point opacity ~0.3–0.6 so overlapping points blend and density emerges. But naive alpha "washes out detail in dense regions and misses sparse points entirely" — so the pros (deepscatter, datashader) do **density-aware rendering**: shade/raster by local point count rather than fixed alpha (datashader's Google-Maps-style raster-per-zoom approach).
- **Point size scaled to density/zoom.** Apple Embedding Atlas computes `pointSize` automatically *from local density* (sparse regions get bigger points), and interpolates size on zoom. Deepscatter does all size/alpha transforms on the GPU so they animate smoothly across zoom.
- **Color by cluster, neutral background.** Color encodes cluster/category; keep background light/dark-neutral so density does the visual work. Nomic renders clusters as "regions of homogeneous color" — color fills, not just dots.
- **Label-on-zoom (LOD).** Show a few big region labels when zoomed out; reveal finer labels as you zoom in. Both Nomic ("topics appear/disappear at zoom levels") and Apple Atlas use hierarchical labels with `level`/`priority` props.

## 2. Computing clusters and placing one label each

- **Don't cluster the high-D embedding for the map — cluster the 2D density.** This is the key Apple insight (paper 2504.07285): run KDE on the 2D projection to a ~1000×1000 grid, then extract clusters by **hill-climbing to local density maxima** (union-find), merge clusters whose peak is near a shared boundary, and truncate each cluster at `d_min = 0.1 × cluster_max_density`. Runs in ~50ms for >1M points (Rust→WASM).
- Alternatives others use: **HDBSCAN** on the UMAP coords (BERTopic, PixPlot option) handles noise/variable density well; **k-means** for a fixed N hotspots (PixPlot default = 20); Leiden/kNN-graph is common in single-cell tools.
- **One label per cluster:** PixPlot uses the **medoid** (the real item nearest the centroid) as the representative. Density-peak methods (Apple) put the label at the **density maximum**, which reads better than the centroid for irregular shapes.
- **Avoiding overlap:** assign labels `priority` + `level`, place greedily highest-priority-first, suppress lower labels that collide, and gate by zoom (standard cartographic dynamic labeling). Apple filters clusters below `autoLabelDensityThreshold` (relative to max density) before labeling.

## 3. Automatic cluster naming

- **c-TF-IDF (class-based TF-IDF)** is the workhorse — treat each cluster as one "document," score terms by how distinctive they are to that cluster vs. the whole corpus, take top-k. Used by BERTopic and Apple Embedding Atlas (Atlas runs c-TF-IDF via SQL range-queries in DuckDB over points inside the cluster polygon). Strip stop words (Atlas defaults to NLTK list).
- Cheaper fallback: **most-common-category** per cluster (you already have Category nodes — use the modal category as a free label).
- Best quality: feed the top c-TF-IDF terms + a few sample titles to an **LLM** for a 2–4 word name (BERTopic's representation models, Nomic's topic labeling).

## 4. Topographic / "Nomic look"

Nomic's contour effect = **KDE heatmap underlay + homogeneous color fills per topic region**, with the dot layer on top. Recipe: rasterize a 2D KDE, draw filled contour bands (or a blurred density texture), trace cluster boundaries into polygons (Apple uses Suzuki contour-tracing on the truncated density grid) and fill each with its cluster color at low opacity.

## 5. Why your UMAP is a blob — and fixes

- **Params first:** set `min_dist = 0.0` (or ~0.1) to pack clusters tightly and open gaps between them; raise `n_neighbors` to ~30 for clearer global structure. This is the documented UMAP-for-clustering recipe and usually fixes "blob."
- **You're force-spreading after UMAP.** Per your CLAUDE.md, projects start at `UMAP × 120` then barnesHut physics runs. **Physics destroys UMAP's cluster geometry** — that's a prime blob cause. For the embedding *view*, render raw UMAP coords with NO physics (physics is for graph mode only). Keep the two modes separate.
- **Spread/jitter:** if clusters still overlap, apply small per-cluster outward gravity or jitter, or just lower `min_dist`. Don't apply central gravity (collapses to a blob — your own note confirms this).
- **Render fixes:** a blob is often *overplotting*, not bad layout — add alpha + density-scaled point size and the structure appears.
